# Evaluation Methodology

This document explains how `ml/evaluation/test_gold_standard.py` measures
the risk-detection model's performance, what each metric means, and the
limitations of the current gold standard dataset.

> **Honesty note:** an earlier version of this README advertised
> precision/recall/F1/accuracy/NDCG/MRR figures with no corresponding
> evaluation code in the repository. This document and the accompanying
> harness replace that — the numbers you get from running `make eval` are
> now actually computed from `backend/dataset/synthetic_gold_standard_with_nli.json`
> via the real embedding model. Treat any numbers quoted in the main
> `README.md` as stale until you've re-run the harness yourself and
> updated them.

## What's being measured

The model (`RiskDetector` in `backend/vector_search.py`) flags a contract
clause as risky if its embedding is similar enough (above a threshold) to
one of three NLI risk hypotheses:

| Category | Hypothesis |
|---|---|
| Termination For Convenience | "Party B may terminate this Agreement for convenience." |
| Uncapped Liability | "Party A's liability for breach of this Agreement is uncapped." |
| Non-Compete | "Party A shall not compete with Party B." |

## How the gold standard is built into a labeled test set

`backend/dataset/synthetic_gold_standard_with_nli.json` contains entries
like:

```json
{
  "category": "Termination For Convenience",
  "nli_hypothesis": "Party B may terminate this Agreement for convenience.",
  "risky_clause": "Company at its sole discretion may at any time alter or cease providing...",
  "safe_clause": "Company shall not alter or cease providing... except upon thirty (30) days' prior mutual written notice..."
}
```

Each entry is split into **two labeled examples**:

- `risky_clause` → label `1` (the model *should* flag this)
- `safe_clause` → label `0` (the model should *not* flag this)

This turns 46 gold-standard entries into ~92 labeled examples, which is
what the 5 tests below actually run against.

## The 5 tests

1. **Risky Clause Detection** — of all `label=1` examples, how many score
   above the threshold against their own category's hypothesis? (this is
   recall, reported as part of the combined Test 1+2 block)
2. **Safe Clause Rejection** — of all `label=0` examples, how many
   correctly score *below* the threshold? (this is specificity / low FPR)
3. **Threshold Sensitivity** — precision/recall/F1/accuracy swept across
   thresholds 0.30–0.90, to show how the choice of threshold trades
   precision against recall, and which threshold maximizes F1.
4. **NLI Hypothesis Similarity** — for risky clauses only, is similarity
   to their *own* category's hypothesis reliably higher than similarity
   to the *other two* hypotheses? This checks that the three hypotheses
   are actually discriminating between categories, not just generically
   matching any legal text.
5. **Category-Specific Accuracy** — precision/recall/F1/accuracy computed
   separately for each of the 3 categories, so a strong category can't
   mask a weak one.

We additionally report **NDCG@5** and **MRR**, treating each category's
hypothesis as a search query over the full pool of 92 examples: a perfect
model would rank that category's risky clauses at the very top.

## Metric definitions

| Metric | Meaning |
|---|---|
| Precision | Of everything flagged, what fraction was actually risky? |
| Recall | Of everything actually risky, what fraction got flagged? |
| F1 | Harmonic mean of precision and recall. |
| Accuracy | Fraction of all examples (risky + safe) correctly classified. |
| False Positive Rate | Of actually-safe clauses, fraction wrongly flagged. |
| False Negative Rate | Of actually-risky clauses, fraction missed. |
| NDCG@5 | Of the top 5 ranked results for a category, how close to ideal ordering? (1.0 = perfect) |
| MRR | 1 / (rank of the first correct result), averaged across category queries. |

## Running it

```bash
cd ml/evaluation
pip install -r requirements.txt
python test_gold_standard.py

# unit tests for the metric math itself (no model/network required)
pytest test_metrics.py -v

# or, from the repo root:
make eval
```

Results print to the console and are also written to
`ml/evaluation/results/latest_results.json` for programmatic use (e.g.
tracking metric drift over time, or plugging into a CI gate).

## Known limitations of the current gold standard

Be upfront about these when quoting any numbers from this harness:

- **Small N.** 46 base entries (17 / 16 / 13 per category) → ~92 labeled
  examples. Confidence intervals on these metrics are wide; a couple of
  examples flipping changes the headline numbers noticeably.
- **Synthetic "safe" clauses.** The `safe_clause` side of each pair was
  generated by prompting an LLM (`amazon/nova-2-lite-v1` via OpenRouter,
  see `backend/synthesize_data.py`) to rewrite the risky clause so it
  contradicts the risk hypothesis. No human legal reviewer has validated
  that these rewrites are actually safe in practice, or that they're
  representative of how real contracts phrase safe terms.
- **Only 3 categories.** Real contracts contain many more risk types
  (IP assignment, indemnification, governing law, etc.) that this gold
  standard doesn't cover at all — performance here says nothing about
  those.
- **Same-source bias.** Risky and safe clauses in a pair are paraphrases
  of each other rather than independently drafted contracts, which may
  make them easier to separate than real-world risky vs. safe clauses
  pulled from different, unrelated agreements.
- **No held-out split.** This harness evaluates on the full gold standard
  every time — there's no train/test separation because the model isn't
  trained on this data directly (it's a pre-trained embedding model used
  zero-shot via similarity), but if the gold standard is ever used to
  *tune* the model or threshold, a held-out split should be introduced to
  avoid overstating performance.

**Recommendation:** before quoting these metrics anywhere external
(investor decks, demo pages, etc.), grow the dataset to more clauses per
category, pull some safe clauses from real (different) contracts rather
than LLM rewrites of the same clause, and ideally have a lawyer spot-check
a sample of both the risky and safe labels.
